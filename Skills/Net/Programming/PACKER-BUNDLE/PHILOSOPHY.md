# PACKER-BUNDLE — Philosophy

A "packer-bundle" is the .NET equivalent of an HCL2 template tree: an
in-memory C# workspace whose contents emit to a directory of `.pkr.hcl` files
plus companion files (provisioning scripts, HTTP-served files, Vagrantfile,
.env). It is the multi-file analogue of a compose-bundle.

This skill captures the recurring pattern for any HCL2-style configuration
that ships as a **directory** rather than a single document.

## HCL2-native, never JSON

Packer (and similar tools) supports two formats: legacy JSON and HCL2. We
target HCL2 (`.pkr.hcl`) exclusively. JSON is frozen at the schema level; HCL2
gets every new feature. The bundle library does not write JSON.

HCL2 features we depend on and that legacy JSON cannot offer:

- `packer { required_plugins { ... } }` for `packer init`
- typed `variable` blocks with validation
- `locals` with computed expressions
- `data` blocks for external data sources
- reusable named `source` blocks
- `build` blocks that reference multiple sources
- multi-file templates
- dynamic blocks, `for` expressions, conditionals, ~80 built-in functions

## Two object families: immutable records and a mutable workspace

A packer-bundle separates two concerns:

| Family | Mutability | Purpose |
|--------|-----------|---------|
| HCL2 block records (`Variable`, `Source`, `Build`, `Local`, `Config`, ...) | **immutable** records, built via `AbstractBuilder<T>` | One-shot, validated values that map to a single HCL block |
| `PackerBundle` | **mutable** class | The whole template tree under construction |

You build records with fluent builders, then add them to the mutable bundle.
The bundle is not serializable — it is the in-memory composition target. When
the user is done composing, a `PackerBundleWriter` materializes it to disk.

```csharp
var bundle = new PackerBundle();
bundle.Variables.Add(new PackerVariableBuilder().WithName("region")
                                                 .WithType("string")
                                                 .Build().Value);
bundle.Sources.Add(new VirtualBoxIsoSourceBuilder().WithName("alpine")
                                                    .WithIsoUrl("...")
                                                    .Build().Value);
bundle.Apply(new DockerHostContributor());
new PackerBundleWriter().Write(bundle, "/tmp/template");
```

## Plugin types are scraped from Go source

Packer's hundreds of builder/provisioner/post-processor types live across ~25
plugin repositories. Their fields are auto-generated by `packer-sdc
mapstructure-to-hcl2` into files named `*.hcl2spec.go`. These files are the
source of truth — every field, every cty type, every required flag, fully
flattened.

We do not scrape HTML docs. We do not write stubs. We fetch the
`.hcl2spec.go` files directly from GitHub, parse the `HCL2Spec()` map literal
with regex (no Go compiler), and emit C# records + builders for every plugin
type. ~70 plugin types, ~145 spec files, ~25 repos.

```
.hcl2spec.go on GitHub
        │
        ▼
PackerPluginScraper (Bundle.Design)
        │
        ▼
scrape/{plugin-type}.json   (one per type, in source control)
        │
        ▼
PackerBundle.SourceGenerator
        │
        ▼
{PluginType}Config record  +  {PluginType}ConfigBuilder
```

When a plugin adds a new field, you re-run the scrape. The new field shows up
on the C# record and on the builder. No human transcription, ever.

## Custom HCL2 writer (we only need to emit, not parse)

There is no mature C# HCL2 library. The three available are HCL1-only, GPL,
or abandoned. But we **only need to write HCL2**, not parse it. Writing HCL2 is
a string-builder problem on par with emitting Ruby or C# source — and we have
plenty of those in the monorepo.

`HclWriter` wraps an `IndentedTextWriter` and offers blocks, arguments,
nested blocks, list-of-lists, raw expressions, comments, blank lines:

```csharp
public class HclWriter : IDisposable
{
    public IDisposable Block(string type, params string[] labels);
    public void Argument(string name, string value);
    public void Argument(string name, int value);
    public void Argument(string name, bool value);
    public void Argument(string name, IEnumerable<string> list);
    public void Argument(string name, IDictionary<string, string> map);
    public void ArgumentListOfLists(string name, IEnumerable<IEnumerable<string>> lists);
    public void Expression(string name, string hclExpression);
    public void Comment(string text);
    public void BlankLine();
}
```

Reading HCL2 is delegated to the `hcl2json` binary when needed (rare).

## Multi-file template output

A real Packer template is split across multiple `.pkr.hcl` files for
readability and `packer init` support. The writer emits exactly:

| File | Content | Source |
|------|---------|--------|
| `packer.pkr.hcl` | `packer { required_plugins { ... } }` | `PackerConfig` |
| `variables.pkr.hcl` | `variable "name" { ... }` blocks | `List<PackerVariable>` |
| `locals.pkr.hcl` | `locals { key = expression }` | `List<PackerLocal>` |
| `sources.pkr.hcl` | `source "type" "name" { ... }` blocks | `List<PackerSource>` |
| `build.pkr.hcl` | `build { sources, provisioner, post-processor }` | `PackerBuild` |
| `scripts/*.sh` | provisioning scripts | `BundleFile` entries |
| `http/*` | HTTP-served files (answer file, ssh keys) | `BundleFile` entries |
| `vagrant/*` | Vagrantfile, metadata.json, info.json | `BundleFile` entries |
| `.env.template` | env var template | `EnvTemplate` |
| `.env` | env values | `EnvValues` |

Companion files are first-class. Building a Packer template is not just about
HCL2 — it is about producing a directory tree the user can drop into a project.

## Contributor pipeline for composition

A bundle is rarely built in one shot. The same contributor pattern as
compose-bundles applies:

```csharp
public interface IPackerBundleContributor
{
    void Contribute(PackerBundle bundle);
}

bundle.Apply(new VirtualBoxBaseContributor(),
             new AlpineIsoContributor(version: "3.21"),
             new DockerHostContributor());
```

Contributors mutate the bundle in place. They can add HCL2 records, add
provisioning scripts, populate the env template, modify the Vagrantfile model.
Each contributor is single-purpose and unit-testable in isolation.

## Shared communicator pattern

Packer plugins embed SSH (~35 fields) and WinRM (~9 fields) connection params
via Go's `mapstructure:",squash"`. Every builder's flat config inlines them.
In C# we model these once as shared `SshCommunicator` / `WinrmCommunicator`
records and compose them into builder configs. Schema-driven generation
detects the squash and substitutes the shared type.

## What this is not

- Not a Packer CLI wrapper. The BinaryWrapper-based `FrenchExDev.Net.Packer`
  package is what you call to actually run `packer build` against the
  generated template.
- Not a runtime executor. The bundle writes files; running them is someone
  else's job.
- Not opinionated about plugins. Every plugin in the registry is scraped;
  none is hand-curated.
- Not a Vagrant wrapper. It can emit a Vagrantfile as a companion file because
  Packer's `vagrant` post-processor expects one — that is the limit.
