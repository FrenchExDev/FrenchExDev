# Plan: Packer.Alpine + Vos VM Orchestration Suite

## Context

Rebuild in C# (with PowerShell integration) the existing PowerShell modules that form two composable chains:

- **Packer chain** (build-time): `Packer.PoSh` -> `Packer.Alpine.PoSh` -> `Packer.Alpine.Docker.PoSh` — creates VM images
- **Vos chain** (run-time): `Vos.PoSh` -> `Vos.Alpine.PoSh` -> `Vos.Alpine.Docker.PoSh` — manages VMs

The result is a "podman-like" developer experience: lightweight VMs running Docker, managed transparently from the host via C# + PowerShell, with multi-hypervisor support (VirtualBox, Hyper-V, Parallels, WSL2).

**Key addition**: Vos must abstract over **both Vagrant and Podman machine** as VM backends. Podman machine commands (init/start/stop/rm/ssh/list/info/inspect/set/reset/cp) are already wrapped in `FrenchExDev.Net.Podman` (187 commands, 55 versions).

## 0. Packer.Bundle — Foundation (HCL2 template model)

**Location**: `Net/FrenchExDev/Packer/src/FrenchExDev.Net.Packer.Bundle/` (directory exists, empty)

This project models the Packer HCL2 template structure as C# records with `AbstractBuilder<T>` builders. It provides:
- **Immutable records** for every HCL2 block type (`source`, `variable`, `build`, `packer`, `locals`, etc.)
- **Scraped plugin type records** for all builder/provisioner/post-processor types (virtualbox-iso, shell, vagrant, etc.) — scraped from official HashiCorp plugin docs, generated by SG (same pattern as BinaryWrapper scrapes CLI help)
- **`HclWriter`** to render records → `.pkr.hcl` files
- **`HclReader`** to parse existing `.pkr.hcl` files → records (via `hcl2json` tool)
- **`PackerBundle`** mutable workspace for composing a complete Packer project
- **`BundleFile`** for companion files (scripts, http, vagrant, .env)

All downstream projects (Packer.Alpine, Packer.Alpine.DockerHost) compose `PackerBundle` instances using these types.

### HCL2 approach

**Target format: HCL2 native (`.pkr.hcl`)**. The PowerShell modules produced legacy JSON — we upgrade to HCL2 which is the official format since Packer v1.7.0. Legacy JSON is still supported but receives no new features.

**No C# HCL2 library exists** (the 3 available are immature/HCL1-only/GPL). But we only need to **emit** HCL2, not parse it. HCL2 writing is a simple string builder problem — same as emitting Ruby (Vagrantfile) or C# (source generators). We build a custom `HclWriter`.

**HCL2 features we gain** (not available in legacy JSON):
- `packer { required_plugins { ... } }` — `packer init` support
- `variable "name" { type, default, validation { } }` — typed variables
- `locals { }` — computed values with functions
- `data "type" "name" { }` — external data sources
- `source "type" "name" { }` — reusable, named builder configs
- `build { sources = [...] }` — reference multiple sources
- Multi-file templates — split across `variables.pkr.hcl`, `sources.pkr.hcl`, `build.pkr.hcl`
- Dynamic blocks, for expressions, conditionals, 80+ built-in functions

**Source of truth**: The `.hcl2spec.go` files in each plugin's Go source code on GitHub. These are auto-generated by `packer-sdc mapstructure-to-hcl2` and contain every field fully flattened — field name, cty type, required status. No stubs, no guessing, no doc scraping.

**No stubs**: Every plugin gets a full record. The Design project crawls ALL plugin repos on GitHub.

**Shared Communicator pattern**: ~35 SSH params + ~9 WinRM params are embedded via `mapstructure:",squash"` in Go and flattened into every builder's `FlatConfig`. In C#, modeled as shared `SshCommunicator` / `WinrmCommunicator` records (composition).

### A. `PackerBundle` — in-memory working object

`PackerBundle` is a **mutable workspace**, NOT a serializable model. Contributors modify it in-place. When done, `PackerBundleWriter` renders it to `.pkr.hcl` files + companion files on disk.

The HCL2 types it contains (`PackerVariable`, `PackerSource`, etc.) are **immutable records with `AbstractBuilder<T>`** builders — you build them, then add them to the bundle.

```
PackerBundle (mutable workspace)
├── PackerConfig            ← record: packer { required_plugins { } }
├── List<PackerVariable>    ← records: variable "name" { type, default, validation }
├── List<PackerLocal>       ← records: locals { key = expression }
├── List<PackerSource>      ← records: source "type" "name" { ... }
├── PackerBuild             ← record: build { sources, provisioner, post-processor }
├── VagrantfileConfig       ← mutable: vagrant/Vagrantfile model (Ruby)
├── EnvTemplate             ← mutable: .env.template model
├── EnvValues               ← mutable: .env values model
├── SortedList<BundleFile>  ← mutable: ALL companion files (scripts, http, vagrant, etc.)
└── IPackerBundleContributor pipeline
```

| Class | Kind | Description |
|-------|------|-------------|
| `PackerBundle` | **class (mutable)** | In-memory workspace. NOT serializable. Contributors modify it in-place |
| `BundleFile` | **class (mutable)** | A companion file: `Name`, `Extension`, `Content`, `Directory`. Mutable so contributors can modify |
| `IPackerBundleContributor` | interface | Extension point: `void Contribute(PackerBundle bundle)` |
| `PackerBundleWriter` | class | Renders bundle → `.pkr.hcl` files via `HclWriter` + writes companion `BundleFile`s to disk |
| `HclWriter` | class | HCL2 text emitter (blocks, arguments, expressions) — custom, no third-party dep |

```csharp
// Mutable workspace — not a record, not serializable
public class PackerBundle
{
    // HCL2 content — mutable containers, contributors build records and add them
    public PackerConfigBuilder Config { get; } = new();        // mutable builder, call Build() at render time
    public List<PackerVariable> Variables { get; } = [];       // add built records
    public List<PackerLocal> Locals { get; } = [];             // add built records
    public List<PackerSource> Sources { get; } = [];           // add built records
    public PackerBuildBuilder Build { get; } = new();          // mutable builder, call Build() at render time

    // Companion models (mutable, contributors modify in-place)
    public VagrantfileConfig Vagrantfile { get; set; } = new();
    public EnvTemplate EnvTemplate { get; set; } = new();
    public EnvValues EnvValues { get; set; } = new();

    // Companion files (mutable, contributors add/modify)
    public SortedList<string, BundleFile> Files { get; } = new();

    // Convenience
    public IEnumerable<BundleFile> Scripts => Files.Values.Where(f => f.Directory == "scripts");
    public IEnumerable<BundleFile> HttpFiles => Files.Values.Where(f => f.Directory == "http");
}
```

### HclWriter — custom HCL2 emitter

We only need to **write** HCL2, not parse it. `HclWriter` wraps an `IndentedTextWriter` and provides:

```csharp
public class HclWriter : IDisposable
{
    public HclWriter(TextWriter writer);

    // Blocks: source "virtualbox-iso" "alpine" { ... }
    public IDisposable Block(string type, params string[] labels);

    // Arguments: key = value
    public void Argument(string name, string value);
    public void Argument(string name, int value);
    public void Argument(string name, bool value);
    public void Argument(string name, IEnumerable<string> list);
    public void Argument(string name, IDictionary<string, string> map);

    // Nested blocks: vboxmanage [ ["modifyvm", ...], ... ]
    public void ArgumentListOfLists(string name, IEnumerable<IEnumerable<string>> lists);

    // Raw HCL expression (for locals, dynamic blocks, etc.)
    public void Expression(string name, string hclExpression);

    // Comments
    public void Comment(string text);
    public void BlankLine();
}
```

### B. HCL2 models — GENERATED from schema

**Scraped from Go source code** on GitHub (same pattern as BinaryWrapper scrapes CLI `--help`).

`Packer.Bundle.Design` fetches `.hcl2spec.go` files from each plugin's GitHub repo (e.g. `hashicorp/packer-plugin-virtualbox/builder/virtualbox/iso/builder.hcl2spec.go`). These files are auto-generated by `packer-sdc` and contain a `HCL2Spec()` method — a flat map of every field with its HCL name, cty type, and required status.

The Design project parses this Go code (simple regex/text parsing on the `HCL2Spec()` map literal — no Go compiler needed) and outputs `scrape/virtualbox-iso.json`. The SG reads these scraped files and emits records + `AbstractBuilder<T>` for each plugin type.

**Go type → C# type mapping** (from `cty` types in `.hcl2spec.go`):

| cty type in Go | C# type |
|---|---|
| `cty.String` | `string?` |
| `cty.Bool` | `bool?` |
| `cty.Number` | `int?` (or `uint?` for sizes) |
| `cty.List(cty.String)` | `List<string>?` |
| `cty.List(cty.Number)` | `List<int>?` |
| `cty.List(cty.List(cty.String))` | `List<List<string>>?` (vboxmanage) |
| `cty.Map(cty.String)` | `Dictionary<string, string>?` |
| `hcldec.BlockListSpec` | nested record list |
| `time.Duration` (→ `cty.String`) | `string?` (Go duration format) |

**No stubs**: every plugin in the 25 repos gets fully scraped. ~70 plugin types, all with complete field lists.

### `Packer.Bundle.Design` — Go source scraper (detailed)

**Purpose**: Fetch `.hcl2spec.go` files from GitHub, parse the `HCL2Spec()` method, output structured JSON for the SG.

**Classes**:

| Class | Description |
|-------|-------------|
| `PackerPluginScraper` | Orchestrator: iterates plugin repos, discovers `.hcl2spec.go` files, runs parser, writes output |
| `GitHubHcl2SpecFetcher` | Fetches `.hcl2spec.go` file content via GitHub API (`GET /repos/{owner}/{repo}/contents/{path}`) |
| `Hcl2SpecParser` | Parses `HCL2Spec()` Go map literal → list of `ScrapedField` (name, ctyType, required). Regex-based — no Go compiler |
| `ScrapedPluginType` | Output model: `PluginKind` (builder/provisioner/post-processor), `TypeName`, `Fields[]`, `NestedBlocks[]` |
| `ScrapedField` | `HclName`, `CtyType`, `IsRequired`, `Description` (from Go comments if available) |
| `PluginRegistry` | Hardcoded list of `(org, repo, paths[])` tuples for all 25 repos. Versioned by Git tag |

**Algorithm**:
1. For each entry in `PluginRegistry`:
   - Fetch repo tree via GitHub API (or use cached)
   - Find all `*.hcl2spec.go` files (glob pattern)
   - Fetch each file's content
2. For each `.hcl2spec.go`:
   - Extract `func (*FlatXxx) HCL2Spec() map[string]hcldec.Spec {` method body
   - Parse the map literal: `"field_name": &hcldec.AttrSpec{Name: "field_name", Type: cty.String, Required: false}`
   - Also parse `&hcldec.BlockListSpec` for nested blocks
   - Map to `ScrapedField` list
3. Output `scrape/{type-name}.json` (one file per plugin type)

**Parsing the `HCL2Spec()` map** — example Go code:
```go
func (f *FlatConfig) HCL2Spec() map[string]hcldec.Spec {
    return map[string]hcldec.Spec{
        "disk_size":  &hcldec.AttrSpec{Name: "disk_size", Type: cty.Number, Required: false},
        "vm_name":    &hcldec.AttrSpec{Name: "vm_name", Type: cty.String, Required: false},
        "headless":   &hcldec.AttrSpec{Name: "headless", Type: cty.Bool, Required: false},
        "boot_command": &hcldec.AttrSpec{Name: "boot_command", Type: cty.List(cty.String), Required: false},
        "vboxmanage": &hcldec.AttrSpec{Name: "vboxmanage", Type: cty.List(cty.List(cty.String)), Required: false},
        "ami_block_device_mappings": &hcldec.BlockListSpec{TypeName: "ami_block_device_mappings", Nested: ...},
    }
}
```

Regex patterns:
- `&hcldec.AttrSpec\{Name:\s*"([^"]+)",\s*Type:\s*([^,]+),\s*Required:\s*(true|false)\}` → field name, cty type, required
- `&hcldec.BlockListSpec\{TypeName:\s*"([^"]+)"` → nested block name

**Error handling**: log warnings for unparseable entries, continue scraping. The SG can handle partial scrape output.

**GitHub API rate limits**: use `GITHUB_TOKEN` env var for authenticated requests (5000/hr vs 60/hr). Same pattern as `GitLabReleasesVersionCollector`.

            new VirtualBoxIsoBuilderBuilder()
                .WithBootWait("10s")
                .WithDiskSize("20480")

                    .WithCpus(4).WithMemory(256).WithNestedHwVirt(true)
                    .Build().ToCommands())
                .Build()));

        bundle.Build.WithSource("source.virtualbox-iso.alpine");
        bundle.Build.WithProvisioner(
            new ShellProvisionerBuilder()
                .WithScripts(bundle.Scripts.Select(f => f.RelativePath).ToList())

### Key design: Backend abstraction (`IVosBackend`)

public interface IVosBackend
{
    string Name { get; }                    // "vagrant" | "podman"

    Task<Result<VosActionResult>> HaltAsync(VosInstance instance, CancellationToken ct);
    Task<Result<VosActionResult>> DestroyAsync(VosInstance instance, CancellationToken ct);

### Async bridging: Channel-based message pump

Cmdlets use `System.Threading.Channels` to bridge async BinaryWrapper calls to synchronous PS pipeline:

```csharp
public abstract class AsyncCmdlet : PSCmdlet
{
    protected abstract Task ProcessRecordAsync(CancellationToken ct);
    protected override void ProcessRecord()
    {
        var channel = Channel.CreateUnbounded<Action>();
        var task = Task.Run(async () => { await ProcessRecordAsync(...); channel.Writer.Complete(); });
        foreach (var action in channel.Reader.ReadAllAsync().ToBlockingEnumerable())
            action();  // WriteVerbose, WriteObject, etc. on cmdlet thread
        task.GetAwaiter().GetResult();
    }
}
```

## Decisions

- **CLI name**: `vos` (with `gvm` as alias in PowerShell module)
- **Podman backend**: BinaryWrapper only (`podman machine` CLI commands via `FrenchExDev.Net.Podman`). No REST API.
- **Implementation order**: Packer.Alpine first (warm-up), then Vos.
